# 2026-10 보안·RTLS 전환 순서

이 변경은 서버 설정, 두 실물 리더, DB 태그 ID, Besu 계약을 함께 바꾼다. `main`에 합쳐도 `DEPLOY_READY` 저장소 변수가 `true`가 아니면 CI는 이미지만 만들고 서버 배포를 건너뛴다. 현장 준비가 끝난 뒤 변수를 설정하고 `Build and Deploy` 워크플로를 `workflow_dispatch`로 한 번 실행한다. 이후 `main` push는 다시 자동 배포된다.

## 2026-10-03 진행 상태

- 홈서버의 DB·루트 `.env`·옛 계약 배포 JSON을 `backups/code-review-cutover-2026-10-03/`에 백업했다. DB 덤프는 `pg_restore -l`로 읽기를 확인했다.
- 운영 DB에 `can_manage_nfc`를 추가해 기존 일반 관리자 6명에게 권한을 유지했고, 데모 관리자와 직원은 제외했다. `M501`·`M502`는 이미 5층의 활성 실물 리더로 등록돼 있다.
- 서버 `.env`에 `RTLS_SIM_KEY`와 리더별 키를 준비했다. 키 값은 문서에 기록하지 않는다.
- `M501`은 기존 스크립트·서비스를 리더의 `backup-2026-10-03/`에 백업했다. 새 스크립트와 전용 `.env`를 설치하고 `ble-reader.service`를 새 경로로 전환했다. 서버 응답의 HTTP `Date`로 서명 시각을 보정하므로 외부 NTP가 응답하지 않아도 전송을 재개할 수 있다.
- 옛 태그 ID 두 개를 `…:1:001`·`…:1:002`로 이전했다. 이전 과정에서 옛 계약에 앵커링된 실물 이력 3건과 연결 NFC 이벤트 6건이 삭제됐고 DB 백업에는 남아 있다. `M501`의 수신 시각과 새 ID의 위치 이력이 갱신되는 것을 확인했다.
- `M502`는 2026-08-15 이후 수신이 없는 장애 상태이며 이번에는 접속·갱신하지 않았다. 복구 시 새 스크립트·전용 키·세 자리 ID를 맞춰야 한다. 새 백엔드가 먼저 배포돼도 M502는 계속 오프라인 상태다.
- 새 백엔드·시뮬레이터·Besu 계약은 아직 배포하지 않았다. 새 배포자·기록자 계정과 가스 비용도 준비 전이다.

1. 운영 DB와 `.env`, `blockchain/besu/deployments/usage-registry.json`을 백업한다. 기존 체인과 DB 이력은 시뮬레이션 데이터이므로, 충돌 시 이력 보존보다 전환 성공을 우선한다. DB의 기존 실물 이력 중 태그 ID와 연결된 앵커 기록은 아래 옛 마이그레이션이 삭제한다. `main` 병합 뒤 서버에서 `git fetch origin main`으로 새 파일을 받아 둔다.
2. 가용한 실물 리더의 실행 스크립트, 서비스 이름, `.env`/하드코딩 설정, 시각 동기화 상태를 확인한다. 각 리더에 서로 다른 임의 `RTLS_READER_KEY`를 준비하고 서버 루트 `.env`의 `RTLS_REAL_READER_KEYS`에 같은 값을 등록한다. 시뮬레이터와 서버에는 동일한 `RTLS_SIM_KEY`를 설정한다. 값은 로그나 문서에 기록하지 않는다.
3. 리더 서비스를 정지한다. 새 `rtls/rtls_reader/send_to_server.py`와 `rtls/.env`를 설치하되 아직 재시작하지 않는다. 새 스크립트는 minor를 세 자리로 보내므로 DB 전환 전에는 시작하지 않는다.
4. 서버에서 `git show origin/main:database/schema.sql`의 내용을 운영 DB에 적용한 다음 `git show origin/main:database/provision_real_readers.sql`을 적용한다. `M501`·`M502`의 `floor=5`, `is_real_hardware=TRUE`, 활성 상태를 확인한다. 기존 비활성 설정은 유지된다.
5. `database/migrations/2026-08-12-tag-scheme-and-drop-serial.sql`의 남은 1·2번 블록을 적용해 실물 태그 ID를 세 자리로 바꾼다. 이 파일은 이미 적용된 3번 컬럼 삭제도 포함하며 재실행해도 된다. 기존 앵커가 달린 실물 이력은 삭제될 수 있다. 태그 ID와 FK 반영 결과를 확인한 뒤 가용한 리더를 재시작한다. `/ingest`가 200을 반환하고 실제 장비 위치가 갱신되는지 확인한다.
6. 공개 개발용 계정과 별개의 Besu 배포자·기록자 키를 준비하고 두 계정에 가스 비용을 충전한다. 서버 `.env`에는 기록자 키와 주소만 두고, 배포자 키는 계약 배포 명령에만 전달한다. 서버에서 backend·simulator를 잠시 멈춘 뒤 `git merge --ff-only origin/main`으로 소스를 새 버전으로 전진시키고, 새 스크립트로 계약을 배포한다. `deployments/usage-registry.json`의 주소·기록자 주소와 온체인 `recorder()`가 일치하는지 확인한다. 옛 JSON은 백업해 두되 새 계약에 옛 이력이 자동 이전되지는 않는다.
7. 서버의 forced-command 경로가 이제 새 `deploy/ci-deploy.sh`를 가리키는지 확인한다. 저장소 작업 트리가 깨끗해야 한다. 새 스크립트는 지정 SHA의 이미지 세 개를 먼저 pull한 뒤 그 SHA로 소스를 전진시킨다.
8. `DEPLOY_READY=true`로 설정하고 워크플로를 수동 실행한다. 배포 후 세 서비스의 이미지 태그가 모두 같은 `sha-<커밋>`인지, 백엔드·시뮬레이터 로그에 서명/체인 설정 오류가 없는지, 실물 위치·대여/반납·온체인 검증이 동작하는지 확인한다.

`DEPLOY_READY`를 켜기 전에는 `main` 병합만으로 서버 코드가 바뀌지 않는다. 서명된 수집이 켜진 백엔드를 실물 리더 준비보다 먼저 배포하면 실물 측위가 멈춘다. 기존 런북의 서버별 경로와 접속 정보는 로컬 전용 `deploy/deployment.md`를 따른다.
