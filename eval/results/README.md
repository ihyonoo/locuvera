# 측위 평가 결과

`python -m eval.positioning`으로 얻은 결과의 기록본이다. 트레이스(수 GB)는 시드로
다시 만들 수 있으므로 저장소에 두지 않고, 수치와 그 출처만 남긴다.

| 파일 | 내용 |
|---|---|
| `run.json` | 시드, 커밋 해시, 시뮬레이션 시작 시각, 전파 상수, 행 수 |
| `results_decisions.csv` | 1단계 판정 축 735조합 (24시간 구간) |
| `results_aggregations.csv` | 2단계 집계 축 240행 (09~12시 구간) |
| `integrity.csv` | 무결성 시나리오 17종 × 이력 10건의 판정 170행 (합의 실증 2종은 CSV에 담기지 않는다) |
| `rtls_live_bench.csv` | `/rtls/live` 성능 — 3구성 × 이력 4규모 × 측정 7종, 84행 |
| `rtls_live_bench_run.json` | 성능 평가의 커밋, 측정 조건, 장비 사양, 이력 생성 시간 |
| `rtls_live_bench.png`, `rtls_live_bench_redis.png` | 성능 평가 그래프 (규모별 폴링 p95, ②·③ 막대 비교) |

한 행은 파라미터 7개와 지표 6개, 표본 수로 이루어진다. 두 단계는 구간이 다르므로
절대값을 서로 비교하지 않는다 — 1단계는 참값 전환 524건, 2단계는 124건 위에서 계산된다.

## 다시 만들기

```bash
python -m eval.positioning collect --hours 24 --raw-hours 3 --start 2026-09-21T09:00
python -m eval.positioning sweep
```

`run.json`의 시드와 커밋 해시가 같으면 같은 트레이스가 나온다. 수집 약 5분,
스윕 약 70분(9워커 기준)이 걸린다.

## 무결성

```bash
bash scripts/dev-up.sh            # 백엔드·DB·Besu가 모두 떠 있어야 한다
python -m eval.integrity --repeat 10 --consensus
```

`goal` 열이 공격 목적이다. **은폐**는 변조한 기록을 정상으로 통과시키려는 것이고,
**훼손**은 정상 기록을 변조된 것처럼 보이게 만들려는 것이다. 증거 보존이 목적인
시스템에서는 둘 다 공격이다.

한 행은 회차 하나의 시나리오 하나다. `run`이 회차이고, 회차마다 다른 장비와 직원을
써서 대여 구역과 이동 경로가 달라진다 — 한 이력에만 성립하는 우연을 걸러내기 위함이다. `expected`는 기대한 결론, `status`는 구현이 돌려준 판정
상태, `matched`는 둘이 맞는지다. 계층별 통과 여부(`db_matches_onchain`,
`db_matches_event`, `tx_input_matches_db`, `tx_sender_matches`,
`transactions_root_matches`)가 함께 실려 어느 계층이 잡았는지를 읽을 수 있다.

`--consensus`는 검증 노드를 실제로 내렸다 올리므로 2분쯤 걸린다. 결과는 화면에만
출력되고 CSV에는 담기지 않는다 — 판정이 아니라 성질의 실증이기 때문이다.

시뮬레이터가 돌고 있으면 같은 Postgres에서 경합이 나 결과가 흔들린다. 평가 중에는
내려 둔다.

## 실시간 위치 조회 성능

```bash
docker-compose -f docker-compose.dev.yml up -d postgres redis   # 시뮬레이터·개발 백엔드는 내려 둔다
python -m eval.rtls_live_bench run
python -m eval.rtls_live_bench plot
```

의료진 화면이 1초마다 부르는 `/rtls/live`를 이동 이력 1만~1,000만 행에서 잰다.
장비 50대, 리더 20대로 고정하고, 세 구성을 같은 벤치 전용 DB 위에서 번갈아 잰다.

| 구성 | 커밋 | Redis | 위치를 읽는 방법 |
|---|---|---|---|
| ① `scan_db` | `aa53d61` | 끔 | 요청마다 이력 전체에 `DISTINCT ON` |
| ② `indexed_db` | `ded8e05` | 끔 | 태그마다 `(tag_id, decided_at DESC)` 인덱스로 최신 1건 |
| ③ `indexed_redis` | `ded8e05` | 켬 | Redis에서 읽고, 없는 태그만 ②의 조회 |

①→②가 쿼리 개선의 몫이고 ②→③이 Redis의 몫이다. 측정은 셋이다 — 핸들러를 HTTP 없이
직접 부른 시간, 클라이언트 N명이 화면처럼 1초마다 부르는 폴링의 응답 시간, 쉬지 않고
부르는 최대 처리량. 이력 1,000만 행의 결과는 다음과 같다.

| 지표 | ① | ② | ③ |
|---|---|---|---|
| 핸들러 p95 | 7,494ms | 20.2ms | 16.7ms |
| 폴링 p95, 동시 10명 | 응답 0/550 | 33.9ms | 31.2ms |
| 폴링 p95, 동시 50명 | 응답 0/2,750 | 28.0ms | 21.1ms |
| 처리량, 동시 10명 | 0 req/s | 95.7 req/s | 112.9 req/s |

②·③은 1만 행에서 1,000만 행까지 값이 거의 같다 — 조회 비용이 이력 규모와 무관하다.
①은 100만 행부터 동시 사용자가 있으면 응답이 30초 타임아웃을 넘는다.

읽을 때 주의할 점:

- 셀마다 한 번만 쟀다. ② 10만 행의 처리량(79·71 req/s)과 ③ 10만 행의 폴링 1명(63.7ms)은
  같은 구성의 다른 규모보다 튄 값이다.
- 폴링 p95에는 응답을 기다리며 줄 선 시간이 들어간다. 화면은 앞 요청을 기다리지 않고
  1초마다 새로 보내므로, ①처럼 요청 하나가 수 초 걸리면 대기가 쌓여 타임아웃(30초)보다
  긴 값이 나온다 — httpx의 타임아웃은 단계별로 걸리기 때문이다.
- 폴링 1명이 10명보다 느린 것은 1초에 한 번만 부를 때 요청 사이에 CPU와 Docker VM이
  쉬었다 깨어나는 비용이 붙기 때문으로 본다.
- 절대값은 `rtls_live_bench_run.json`의 장비(Apple M5, Docker 10코어·7.7GB) 기준이다.
  규모에 비례하느냐 무관하느냐는 장비가 바뀌어도 유지된다.

백엔드는 각 커밋의 배포용 `backend/Dockerfile`로 빌드해 Postgres와 같은 Docker 네트워크에서
띄운다. 호스트 프로세스로 띄우면 요청마다 새로 맺는 DB 연결이 Docker Desktop의 포트
포워딩을 거치고, 동시 50명에서 30초쯤 지나면 프록시가 연결을 거부한다. 셀마다 남은 세션을
끊고 `CHECKPOINT`한 뒤 20초 쉰다 — 앞 셀의 무거운 스캔과 이력 삽입 뒤 체크포인트가 다음
셀을 2~3배 느리게 만들었다. 전체 실행은 약 1시간 40분 걸린다.
